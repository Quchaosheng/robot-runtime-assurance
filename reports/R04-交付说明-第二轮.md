## 2. 黑盒接入：workbench-mobile-home-robot

**做法**：新增 `workbench` 传输，只用它的公开 CLI（`sim_cli.py run ...`），读它发布的
证据包。三条规则保证这真的是黑盒：

| 规则 | 实现 | 测试 |
|---|---|---|
| 不 import 被测系统 | 从不把它加入 `sys.path` | `test_the_harness_never_imports_the_subject` |
| 自述不算证据 | `device_state` / `task_terminal` 标记 `subject_claim`，被排除在独立观测外 | `test_a_subject_self_report_is_never_an_independent_observation` |
| 校验和要自己算 | harness 自己 hash 它的 `checksums.sha256` | `test_the_normal_run_publishes_a_verifiable_bundle` |

**实际发现的三件事**（都不是走形式）：

1. `SIGKILL` 的运行**不发布任何产物**（exit `-9`），只留下 `.partial` 目录。
2. 在此之前，"没发布产物"和"根本没去看"在证据里长得一模一样。
3. workbench 的 `sequence_no` 不是 task epoch；我一开始按 epoch 映射，导致每条 ACK
   都像迟到的，oracle 正确地判了 refuted —— **工具抓住了自己的 bug**。

## 3. I2 从"不可证伪"变成"两面可测"

原来的 I2 是结构性的：验收器没有通往设备的代码路径，所以"模型绕过执行器"这件事
在这个工具里永远不会失败。**这句话是对的，但它不构成对被测系统的检验。**

现在场景可以声明 `raw_probes`，runner 发一条原始关节指令，设备的回答决定判定：

| 设备行为 | 判定 | 理由 |
|---|---|---|
| 每条都拒绝 | `confirmed` | 执行器边界存在 |
| 任意一条照做 | `refuted` | 边界不存在 |
| 压根没发探针 | `insufficient_evidence` | 沉默不等于合规 |
| 发了没有回应 | `insufficient_evidence` | 没有证明任何事 |

`negative-controls/sut-accepts-raw-command` 用**真的会乱来**的设备跑这条规则。

## 4. SocketCAN：真实现 + 诚实不可用

按被测机器人已有的帧格式实现（`0x100` 命令 / `0x101` ACK / `0x102` STOP /
`0x103` STOP ACK），保持与设备侧同一语义，不发明第二套协议。

本机实测：

```
AF_CAN 可用       : True
ip link add vcan0 : RTNETLINK answers: Operation not permitted
socketcan 传输    : UNAVAILABLE — vcan0 is absent (needs CAP_NET_ADMIN ...)
```

所以 CAN 场景返回 `insufficient_evidence`，并在时间线里写明原因。
**没有做 mock CAN 总线** —— 那会让验收矩阵里的 CAN 行彻底失去意义。

## 5. RoboTraceOpt：按文件契约接入，不当依赖

读它发布的 `association-evidence-summary/v1`，**自己重算**每个 sha256：

| 情况 | 判定 |
|---|---|
| 摘要与产物一致 | `confirmed`（对**产物**的观测） |
| 产物在发布后被改动 | `refuted` |
| 本地没有对应产物 | `insufficient_evidence`，并点名缺什么 |
| 没有一个可重算的摘要 | `insufficient_evidence`，绝不写成 ok |

已经用它的真实 fixture（`w1_real_summary.json`，642 / 99127 / 4801 条）验证解析。

## 6. workbench 侧的真 bug 与修复

**问题**：`run_scenario` 的 `except BaseException` 能清掉所有 Python 能捕获的错误，
但 `SIGTERM` / `SIGKILL` 根本不会变成异常，于是留下
`runs/.<run-id>.xxxx.partial/` 永久垃圾。

实测三种信号：

| 信号 | 退出码 | 是否发布产物 | 是否留 `.partial` |
|---|---|---|---|
| SIGINT | 1 | 发布 `INTERRUPTED` | 否 |
| SIGTERM | -15 | 无 | **是** |
| SIGKILL | -9 | 无 | **是** |

**修复**：下次运行前清扫过期暂存目录，`STALE_STAGING_SECONDS = 700`
（长于最长允许的 600 s manifest 超时）。新鲜目录一律不动，因为可能属于正在跑的进程；
只删目录，不删同名普通文件。三条测试覆盖这三个边界。

复现报告：`workbench-mobile-home-robot:docs/qa/killed-run-staging-residue.md`

## 8. 仍然没做（明确边界）

| 没做 | 原因 |
|---|---|
| 真机 / 硬件回放 | 明确不做，不承诺 |
| gRPC 适配器 | 与 ROS 2 / workbench 两条路径能力重叠，暂不需要 |
