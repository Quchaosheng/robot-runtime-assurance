# 背诵卡（Robot Runtime Assurance and System Acceptance）

> 被问到任何一点，先给**结论**，再给**证据**，最后给**边界**。不要背形容词，背数字和文件名。

---

## 1. 一句话

> 我做的是一个**黑盒验收器**：把机器人运行时当成不透明的被测系统，注入故障，只用三态判定
> `confirmed / refuted / insufficient_evidence` 给出结论，并产出别人可以离线复核的证据包。

区别一句话：**别的工具告诉你"消息收到了"，我的工具回答"取消之后机器人是否真的停了"。**

---

## 2. 为什么值得做（30 秒版）

现有工具能回答：进程是否退出、消息是否收到、trace 多久、节点是否起来、数据能否回放。

但交付一个陌生机器人系统时，系统负责人真正要问的是：

1. 取消任务后，机器人**真的停了吗**？
2. 旧任务的**迟到 ACK 会不会污染新任务**？
3. 设备断连后是否进入**预期终态**？
4. 资源冲突时，第二个任务**被拒绝**了还是被排队了？
5. 这次结论是**通过、失败、还是证据不足**？
6. 这个验收**别人能复核吗**？

---

## 3. 八条不变量（最重要的资产，能背就背）

```
I1  未注册的场景不能执行
I2  PolicyProposal 不能绕过执行器直接发设备动作
I3  资源 claim 冲突时，后续任务必须被拒绝
I4  取消任务必须升级为 STOP
I5  STOP 之后必须收到设备 ACK 与终态
I6  迟到 ACK 不能完成或污染新的 run
I7  断连/进程死亡/超时后必须进入规定终态
I8  证据不完整时必须是 insufficient，不能假装通过
```

**I2 的特殊说明（一定要主动讲，否则会被追问）**：
> I2 我不是用一个 claim 去测的，是**结构性保证**——验收器只认识 `start / cancel / stop` 和一个 action 名字，
> 它没有任何一条代码路径能直接碰设备。所以"模型绕过执行器"不是我能测失败的用例，而是我根本越不过去的边界。
> 可观测的那一半（执行器会不会拒绝非法 claim）我用 `negative-controls` 去测。

---

## 4. 三态判定（差异化核心）

| 状态 | 含义 | 允许给出的条件 |
|---|---|---|
| `confirmed` | 必要证据齐全且不变量成立 | **必须有独立观测**：设备状态、或 SIGKILL/崩溃 |
| `refuted` | 证据明确证明不变量被违反 | 有具体事件与它矛盾 |
| `insufficient_evidence` | 缺少必要证据，无法判断 | 事件缺失、没有观测、记录停得太早 |

**必须会讲的一句话**：
> ACK 是被测系统自己的**声称**，不是证据。所以只要没有独立观测，即使 ACK 一切正常，也只能是
> `insufficient_evidence`。这是有测试钉住的：`test_no_independent_observation_caps_a_confirmed_verdict`。

还有一条容易加分的细节：
> **验收器自己发起的关机不算证据**。`sut_exit` 带 `requested: true` 时不计入独立观测，
> 否则每次干净退出都会自我确认。测试：`test_a_harness_requested_exit_is_not_evidence`。

## 5. 故障注入：为什么是"会话层"而不是"网络层"（必背，这是最容易被挑战的点）

本机实测（`assure doctor` 会打印）：

```
tc netem       不可用（需要 CAP_NET_ADMIN）
iptables       不可用
vcan 设备      不可用（RTNETLINK: Operation not permitted）
cgroup 写入    不可用
ptrace         不可用
```

所以我的注入点是**验收器与被测系统之间的对话**：ACK 不发、ACK 晚发、ACK 带回旧 epoch、
进程被杀、资源被占、到点取消。

> **我不会声称"验证了内核 CAN 栈在丢包下的行为"**，因为我给不出那个证据。我能给的是：
> 当对话是恶意的时候，运行时和设备协议是否还守在安全态。

追问「那不就不够真实？」——回答：
> 真实的那一半我用第二条传输补上了：ROS 2 action 走真实 DDS，截止时间、取消、STOP 服务、
> 状态话题都是真的。mock 那条只负责把判定链跑成确定性。

## 6. 五类故障 × 三个场景（数字要准）

**场景 13 个**（`assure list`），其中 **3 个必须不通过**：

| 必须不通过的 | 期望 | 为什么它必须失败 |
|---|---|---|
| `cancellation/stale-ack-does-not-pollute-next-task` | refute | 如果 oracle 不再识别 stale epoch，它会变 pass，CI 就红 |
| `negative-controls/sut-grants-conflicting-claim` | refute | 如果 I3 不再抓得住"冲突被批准"，它会变 pass |
| `negative-controls/sut-ignores-cancel` | refute | 如果 I4/I5 不再要求 STOP ACK，它会变 pass |

再加一个 `failures/evidence-missing` 期望 **insufficient**：它证明"不可知"这条路仍然是活的。

**故障**：`drop_ack` / `delay_ack` / `stale_ack` / `kill_sut` / `task_timeout` / `claim_conflict`
→ 你说的五类全部覆盖（ACK 丢失、ACK 迟到、进程被杀、任务超时、资源 claim 冲突），
stale_ack 是我加的第六条，专门打"迟到 ACK 污染新任务"。

**"故障没真的注入"会被单独标记**：`fault_coverage()` 里每个故障都要 `exercised: true`，
否则整轮判定被 `fault_not_exercised` 挡掉，不会算成通过。

## 7. 证据包与回放（被问"凭什么信你"时用）

```
runs/<scenario>--<id>/
  deterministic/     scenario / timeline / verdict / coverage  ← 重算必须得到同一个 digest
  observed/          原始事件流                                  ← 可比对，不可重放
  manifest.json
  checksums.sha256
  COMPLETE                                            ← 最后才写，半个包永远不像一次完成的运行
```

**三种 replay，我只承诺一种半**：

| 类型 | 状态 |
|---|---|
| evidence replay（从证据包重算判定） | **已实现**，digest 必须一致 |
| fixture replay（确定性 mock 上重跑整场） | **已实现** |
| hardware replay（真机逐位复现） | **明确不做**，不承诺 |

测试 `test_tampering_with_the_timeline_is_detected`：改一行 timeline，`assure verify` 立刻报错。

## 8. 与旧项目的关系（一定被问）

| 仓库 | 角色 |
|---|---|
| `workbench-mobile-home-robot` | 被测系统 / 参考机器人 / 场景来源 |
| `embodied-agent-runtime` | 任务执行核心（独立进程，通过公开接口） |
| `ros2-control-vcan-motor-demo` + ROS 2 Demo | 参考底盘与设备夹具 |
| `RoboTraceOpt` | 可选的跨层时延观测插件 |
| **robot-runtime-assurance** | 外部黑盒验收器 |
| `quard-star-riscv64-net` | 冻结，不接入 |

**为什么独立仓库（一句话）**：
> 我要证明的是黑盒验收能力。验收器一旦 import 被测系统的内部模块，黑盒边界当场就不成立了。
> 所以 `tests` 里连被测系统的消息包都不 import——ROS 2 那条路径用的是系统自带的
> `Fibonacci` action 和 `std_srvs/Trigger`，没有一个 IDL 来自被测系统。

**为什么没有把旧代码搬过来**：
> 只有 4 个模块值得搬（事件存储、场景注册的失败关闭、证据包写入、provenance 哈希，约 2k 行），
> 其余重写。旧仓库当时是 `44 errors during collection`（editable install 指向不存在的路径），
> 三个目录都声明顶层 `workbench` 包，`_paths.py` 漏了 `libs/kernel`——直接升级等于在坏地基上加层。

## 9. 数字（可以直接背）

- **13 个场景**，其中 **3 个必须 refute、1 个必须 insufficient**
- **52 passed / 1 skipped**（有 ROS 2 时）；无 ROS 2 时 **51 passed**，且 ROS 2 场景被记为
  `transport_unavailable`（不是静默跳过）
- **两种 CI pass**：无 ROS 2 跑一遍、有 ROS 2 再跑一遍（`ci/run-matrix.sh`）
- 默认路径**零运行时依赖**（纯 stdlib）
- 核心判定 `oracle.py` 是**纯函数**：无时钟、无 I/O、无随机

## 10. 已知边界（主动讲，比被问出来强）

1. 故障只在**验收器↔被测系统边界**注入，不进入被测系统内部。
2. mock SUT 是替身，证明的是判定链，不是机器人物理。
3. 只有 ROS 2 action 这条是真实中间件；gRPC / SocketCAN 没做（本机 vcan 不可用）。
4. **不是功能安全认证**，README 第一屏就写了这句中英文声明。
5. ROS 2 自带的 pytest 插件与 pytest 9 不兼容（collection 直接 INTERNALERROR），
   CI 里用 `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` 规避——这是环境事实，不是我藏起来的问题。

## 11. 被追问时的高频三问

**Q：这不就是 chaos engineering 吗？**
> 不是。chaos 的产物是"系统还能不能活"，我的产物是**三态判定 + 可复核证据**。
> 而且我明确拒绝了网络层 chaos，因为本机给不出那个证据。

**Q：没有真机，凭什么说能验收机器人？**
> 我不说能验收任意机器人。我说的是：**交付边界、判定规则、证据格式**这三件事已经跑通，
> 接真机只需要再加一个 transport，判定层不用改。ROS 2 那条路径就是我拿真实中间件做的证明。

**Q：为什么不直接用 launch_testing / rosbag2 / Jepsen？**
> 它们各自解决一段：launch_testing 管进程，rosbag2 管记录，Jepsen 是为分布式数据库设计的。
> 没有一个是"给我一个陌生机器人，告诉我它能不能交付、并且我能复核"。
> 我的价值在**把它们之间缺的那层**补上：不变量 → 故障 → 三态判定 → 证据包。
> 依赖上我也守纪律：`python-can` 是 LGPL，所以没进核心；ROS 2 全部是 Apache-2.0，本地
> `package.xml` 逐个核过。

## 12. 现场演示口令（30 秒）

```bash
python3 -m assurance.cli doctor                                 # 这台机器能测什么、不能测什么
python3 -m assurance.cli list                                   # 13 个场景，含 3 个必须失败
python3 -m assurance.cli run cancellation/cancel-then-stop      # 通过
python3 -m assurance.cli run negative-controls/sut-ignores-cancel   # 样本被 refute，工具 PASS
python3 -m assurance.cli report runs/negative-controls-sut-ignores-cancel
python3 -m assurance.cli verify runs/nominal-normal-task        # 校验和 + 重算判定
```

演示时强调一句：
> **负对照的 PASS 和正常场景的 PASS 含义不同**——负对照的 PASS 意思是"我逮住了这个坏样本"。
> 这就是 `expect_verdict` 存在的原因：CI 能区分"工具坏了"和"样本坏了"。
