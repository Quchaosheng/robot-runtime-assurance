## 3. 过程中发现的四个真实问题（这些比代码更值钱）

### 3.1 我自己的工具差点"自我确认"

第一版 runner 在关机时补一条 `sut_exit`，oracle 就把它当成独立观测，
结果**每次干净退出都会 confirmed**。修法：`requested: true` 的退出不计入独立观测。
这条现在是回归测试。**这是"证据不足不能假装通过"在实现层面最容易被悄悄破坏的地方。**

### 3.2 负对照的 PASS 和正常场景的 PASS 含义不同

一开始负对照（故意做坏的被测系统）被 refute，工具就判 FAIL —— 但工具其实工作正常。
修法：场景声明 `expect_verdict: pass | refute | insufficient`，CI 拿"实际结论"和"期望结论"比。
**没有这个字段，CI 无法区分"工具坏了"和"样本坏了"。**

### 3.3 I4/I5 一开始是空的

最早期 `cancel_then_stop` 只检查"发了 cancel 之后有没有状态上报"，
所以一个**完全无视取消**的 SUT 也能通过。补了真正的 STOP 命令 + STOP ACK + settled state 之后，
`negative-controls/sut-ignores-cancel` 才真的被 refute。
**这说明：负对照的价值不在于"看起来严格"，而在于它能逼出判定规则的空洞。**

### 3.4 ROS 2 自带 pytest 插件与 pytest 9 不兼容（环境事实）

sourced ROS 2 后直接 `pytest` 会在 collection 阶段 `INTERNALERROR`
（`launch_testing` 用的是 pytest 7 时代 hook spec）。规避方式：
`PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 pytest -p no:randomly`，已写进 `ci/run-matrix.sh`。

## 4. 与规格的两处偏离（都是我判断后改的，说明理由）

1. **`adapters/ fault_injection/ replay/ report/` 没有做成空目录。**
   这些能力都在 `transports.py`（适配）、`runner.py`（注入）、`evidence.py`（报告/回放）里，
   拆成空目录只是摆设。如果你要按目录讲故事，我可以拆，但那就是为了目录好看而拆文件。

2. **ROS 2 SUT 用的是系统自带的 `Fibonacci` action + `std_srvs/Trigger`。**
   不用被测系统自己的 IDL，是因为**一旦 import 对方的消息包，黑盒边界就没了**。
   这是黑盒性最容易被破坏的地方，我宁可让 action 名字难看一点。

## 5. 还没做的（明确边界）

| gRPC 适配器 | 第二版；proto 生成桩会引入编译依赖 |

| 真机 / 硬件回放 | 明确不做，不承诺 |
| Web UI、VLA、多机 | 按你的"不要做"清单，全部没有 |

## 6. 下一步建议（按性价比排序）

1. **接上真正的被测系统**：把 `workbench-mobile-home-robot` 的任务接口包一层 ROS 2 action，
   当成 `ros2action` 传输的被测对象。判定层一行不用改。
2. **把 I2 做成正面可测**：现在 I2 只有负对照（执行器拒绝）。要正面测它，
   需要一个"会接受非法动作"的 SUT 变体，用来证明验收器能抓出来。
3. **接 RoboTraceOpt**：把 `latency-report.json` 作为证据包附件，让"时延"也进入判定，
   而不是只做旁证。
