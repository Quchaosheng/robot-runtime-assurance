# 具身智能系统验收 / 故障注入 / 证据工具链：可行性研究

> 研究对象：`embodied-system-assurance`（暂名 `robot-assurance-kit`）
> 研究日期：2026-10-25　环境：本机 Ubuntu 24.04 / 容器内（CapEff=0、NoNewPrivs=1、无 sudo）
> 结论一句话：**方向成立，"五个仓库合体 + 自研全栈"不成立。第一版应该缩小成"两小时能跑通的确定性核心 + 一条真实 ROS 2 动作路径"，而不是六个模块齐上。**

## 1. 本机实测：能力边界（这一节决定第一版能写什么）

全部在 2026-10-25 实测，不是推断。

| 能力 | 结果 | 对设计的影响 |
|---|---|---|
| ROS 2 Jazzy | ✅ 已装（290 包），`rclpy` 可用 | 可用作真实测试对象 |
| 跨进程话题通信 | ✅ 3 条消息 0.6 s 送达 | 黑盒适配器可行 |
| **ROS 2 Action 往返** | ✅ 正常/延迟 ACK/丢 ACK 三态均可复现 | **"迟到 ACK/丢 ACK"可以在真实 DDS 上验证，不用 mock** |
| Action 截止时间 | ✅ 2 s 截止：正常 0.2 s 确认；延迟 ACK 与丢 ACK 都在 2.6 s 判 `DEADLINE_EXCEEDED` 并发取消 | 截止时间语义原生可用 |
| python-can **virtual bus** | ✅ 收发通（`interface='virtual'`，不需要内核 vcan） | CAN 测试对象不依赖 root |
| **vcan 内核设备** | ❌ `ip link add type vcan` → `EPERM`；`RTNETLINK: Operation not permitted` | **所有 `vcan0` 方案在本机不可用** |
| 用户命名空间 | ❌ `unshare -rn` → `cannot open /proc/self/uid_map` | 无法绕过 |
| `/dev/kvm` | ❌ `open()` EACCES | 虚拟机夹具不可行（QEMU/TCG 可跑但慢，且 loopback CAN 也要 root） |
| `tc netem` / `iptables` | ❌ 需要 CAP_NET_ADMIN | 网络层丢包注入**必须**改成在会话层实现 |
| `/dev/net/tun` | ✅ 存在（但无 CAP_NET_ADMIN 建不了设备） | 无用 |
| 杀子进程 / SIGSTOP | ✅ 正常 | "进程被杀"故障可行 |
| `ptrace` 自己的子进程 | ❌ `ptrace(PTRACE_SEIZE) EPERM` | `strace` 类观察器不可用 |
| cgroup 写入 | ❌ Permission denied | cgroup 资源限制类故障不可行 |
| `pip` / PyPI | ✅ 可用 | 依赖可装 |
| GitHub API / raw | ⚠️ 间歇性 TLS 失败，API 限流 60/h（已用尽） | 对照调研只能做抽样，不代表穷尽 |
| `apt-get download`（无 root） | ✅ 可下载 `.deb` 并解包到本地 | **BehaviorTree.CPP、gRPC 头文件可以本地装，不用 root** |

### 1.1 被实测推翻的三个假设

1. **"用 vcan0 当被测设备"** —— 本机不可能。必须改为：
   - 首选：**ROS 2 Action 的服务端/E CU 模拟器**（纯用户态，已实测）；
   - 备选：`python-can` virtual bus（已实测）；
   - 真 vcan 支持写成**可选后端**，`doctor` 里检测到 `EPERM` 就明确报 `vk_absent`，而不是静默跳过。
2. **"用 netem/iptables 注入丢包"** —— 不可能。丢包必须在**会话层**做：适配器把每个请求的 ACK 相关性（`task_id + epoch + retry_count`）显式记录，注入器决定"这条 ACK 不发/晚发/发错 epoch"。好处是可控可重放，坏处是不能声称"验证了内核 CAN 栈在丢包下的行为"。
3. **"跑完整 workbench 测试套件作为基线"** —— 现状是 `44 errors during collection`（`ModuleNotFoundError: workbench.kernel`，editable install 指向不存在的路径）；打补丁装好后是 `2625 passed / 33 failed`，33 个失败里 12 个是缺 `docker`、约 19 个是无写权限，**核心子集 195 项全绿**。也就是说：**旧仓库的"证据优先"内核是好的，但"一条命令跑通"这个第一版验收条件，旧仓库自己现在就不满足。**

## 2. 关键判定：第一版的六模块哪些能真做

| 模块 | 第一版可行度 | 理由 / 实测依据 |
|---|---|---|
| **Scenario Registry**（JSON Schema：任务、前置条件、资源、超时、预期终态） | ✅ **必须做，且是真正的差异化** | 旧仓库的 registry 只管 `seed/fault_type/timeout_s`，**没有前置条件、没有资源、没有预期终态**（已核对 `scenario.schema.json` 仅 15 行）；S1/S2 开源项目也没有。这是六模块里唯一"别人都没做"的结构性缺口 |
| **Black-box Adapter** | ⚠️ **只做 ROS 2 Action 一条** | gRPC 需要额外写 proto + 生成的桩，属于第二版；SocketCAN 用 python-can 或 ROS 2 消息代理。**三种适配器一起上会把第一版从 2 周拖成 2 个月** |
| **Fault Injector（五类）** | ⚠️ **三种原样可做，两种必须改定义** | 见 §2.1 |
| **Oracle / Verdict** | ✅ **核心，且已用 60 行 spike 验证** | 纯函数、可重放、能区分 `confirmed / refuted / insufficient_evidence`，见 §2.2 |
| **Evidence Bundle** | ✅ **直接借鉴旧仓库，不要重写** | 旧仓库的 `checksums.sha256 + identity_hash + provenance_hash + 拒绝覆盖的原子发布` 是正确的，且已被 2.6k 测试覆盖 |
| **Replay / Report** | ✅ **但"确定性重放"要限定语义** | 重放的是**判定函数**，不是机器人物理过程。见 §2.3 |

### 2.1 五类故障的真实可行性

| 故障 | 原设想 | 本机可行性 | 第一版建议 |
|---|---|---|---|
| 设备 ACK 丢失 | 不发 ACK | ✅ 已实测（`drop_ack` 模式，2 s 判超时） | 原样保留 |
| ACK 迟到 | 晚发 ACK | ✅ 已实测（4 s 延迟 vs 2 s 截止） | 原样保留；**验收点 = 迟到 ACK 不能确认下一个任务** |
| 进程被杀 | kill -9 被测进程 | ✅ 子进程可杀 | 保留，但要定义"杀谁"：杀 SUT 节点，观察**编排层**是否 fail-closed，而不是杀测试框架自己 |
| 任务超时 | 超时 | ✅ 已有 deadline 语义 | 保留 |
| **资源 claim 冲突** | 两任务抢同一资源 | ⚠️ **只有编排层做 claim 才有意义**；本机没有集群/多机 | **降级为"单进程内的资源租约表"**：测试框架侧维护 claim，断言 SUT 在冲突时拒绝而不是排队或静默覆盖。不要伪装成分布式锁 |
| （新增建议）**取消 vs 完成竞争** | — | ✅ 已实测：截止时间触发后 `cancel_goal_async` 被服务端接受 | **建议替换掉"资源 claim"里的分布式幻想**，这个更有价值且可复现 |

> 关键取舍：**"五种故障都能进入预期安全状态"这个验收条件，在单机 + 无 root 下只能对 4 种成立**（ACK 丢失、ACK 迟到、进程被杀、超时）。资源冲突必须以"框架侧租约表"的形态实现，并在报告里写明它的作用域，否则就是给面试官一个可被一句话戳破的宣称。

### 2.2 Oracle 已经跑通（实测代码，40 行）

```python
def verdict(timeline, tasks):          # 纯函数：只吃"已记录的时间线"
    ...                                # 无时钟、无 I/O、无随机
```

三种时间线的输出：

| 输入 | 判定 |
|---|---|
| 干净执行 | `A: confirmed(ack_within_deadline)` / `B: confirmed` |
| **A 的 ACK 被标成 B 的** | `A: refuted(no_ack_recorded)` / `B: **refuted(late_ack_from_previous_epoch)**` |
| ACK 晚于截止 | `A: refuted(ack_after_deadline)` |
| 只有 ACK、没有独立观测 | 自动降级为 `insufficient_evidence(no_independent_observation)` |

并且：`json.dumps → json.loads` 后重跑，判定与摘要完全一致（`707a2e300f4bf4c7`）。
**这证明了三件事**：判定可以是纯函数；"迟到 ACK 污染新任务"可以被机械识别；证据不足时不会假装通过。

### 2.3 "固定 seed 可以重放"要限定语

- **能重放的**：判定函数、场景清单、时间线 → 结论的映射、报告生成。**必须做到逐字节一致**（sha256 相同）。
- **不能重放的**：DDS 发现时序、调度抖动、真实传感器读数、被杀进程的内存状态。
- 因此证据包应当把两者**分开存**：`deterministic/`（可重放并校验哈希）与 `observed/`（原始时序，仅可比对不可复现）。第一版就把这个分区写进 schema，比事后补丁便宜得多。

## 4. 代码复用：升级旧仓库，还是新开？

### 4.1 为什么不能直接升级 `workbench-mobile-home-robot`

实测事实（2026-10-25，`b5274f6`）：

- **打包已坏**：editable install 指向 `/home/chaosheng/Documents/Codex/2026-10-19/.../repo-main`（不存在）→ `import workbench.kernel` 失败 → `pytest` **44 个收集错误**；README 里的 `python -m pytest -q` 直接跑不了。
- **命名空间冲突**：`libs/kernel/workbench/`、`libs/hardware/workbench/`、`libs/application/workbench/` **三个目录都声明顶层 `workbench` 包**（已核实三个 `__init__.py` 均为 0 字节）。`PYTHONPATH` 顺序决定谁生效，另两个被静默丢弃。这是包装缺陷，不是测试瑕疵。
- **`tools/scripts/_paths.py` 漏了 `libs/kernel`** → 所有 CLI 在未安装时启动即失败。
- **领域模型焊死**：`verifier.py` 里 `verify_workspace_clearance` 硬编码 `{"blue_cylinder": ..., "red_block": ...}`；六个入口全部吃 20+ 字段的家用机器人 `WorldState`。复用判定器 = 复用整个领域。
- **脚本路径其实是"编造"验证事件**：`run_evaluation.py` 用 profile 里的硬编码 `status` 拼 `verification` 事件，并没有调用 verifier（已核对）。仓库对此是诚实的（`SCRIPTED_FIXTURE`、`release_eligible=false`），但这意味着**没有一个"跑通"的端到端验收可以继承**，只有脚手架。

结论：**升级它 = 在 113k 行、打包损坏、领域耦合的仓库上重做 60% 的模块**。

### 4.2 为什么也不能从零重写

旧仓库里有约 2.3k 行**零依赖、已被 195 项核心测试覆盖、且真正 fail-closed** 的代码，和你新项目的四个模块一一对应：

|---|---|---|---|
| `libs/kernel/.../event_store.py` | 958 | 证据 / 回放 | **搬迁**（stdlib sqlite3，无领域知识） |
| `libs/kernel/.../scenario_registry.py` + `scenario_contract.py` | 274 + ~430 | 场景注册 | **搬迁语义，重写 schema**（它没有前置条件/资源/终态） |

## 5. 差异化到底站不站得住

**站得住的部分**：
1. **三态判定 + 证据不足不通过** —— 多数测试框架只有 pass/fail/skip。你的 `insufficient_evidence` 是真正的差异化，且已在 spike 里跑通。
2. **"迟到 ACK 不得污染下一任务"** —— 这是可被机械检查、可被外部复现的**具体**安全性质，比"支持故障注入"这种宣称值钱得多。
3. **证据包可离线复核** —— 哈希 + 时间线 + 判定，评审者不需要重跑就能核对。

**站不住 / 需要收敛的部分**：
1. **"黑盒"这个词要限定**。你决定不了对方用什么传输；第一版只有 ROS 2 Action 一条路径，"黑盒"= "不 import 对方内部模块"，仅此而已。写清楚。
2. **"仿真设备"不等于"真实设备"**。所有结论必须是"在某虚拟 ECU 上"，不能外推到真机。
3. **"确定性重放"只能对判定链成立**（§2.3）。
4. **"资源 claim 冲突"** 在单机上是框架侧租约，不是分布式锁（§2.1）。

## 6. 主要风险（按严重度）

| 风险 | 后果 | 缓解 |
|---|---|---|
| **把"没跑"当"通过"** | 整个项目失去意义 | 强制三态；`insufficient_evidence` 是默认值；空证据包直接判失败而不是跳过（旧仓库的 `evidence_refs` `minItems: 1` 就是这个思路） |
| **拿日志回放冒充验收** | 面试时一句话被戳破 | 证据包分区 `deterministic/` vs `observed/`；报告里明写"不可复现项" |
| **故障注入靠 root 能力** | 在评审/CI 环境直接崩 | 全部走会话层注入（已实测可行）；`doctor` 显式声明哪些后端不可用 |
| **被测量对象编译不出来** | 第一版卡在环境上 | 先用**自己写的 60 行假 SUT**（已实测）跑通全链路，再接 EAR；编译脚本单独交付 |
| **LGPL/EPL 污染** | 分发时踩雷 | `python-can` 作为可选 extra；jepsen 只借鉴思想；MIT 借鉴保留声明 |
| **范围蔓延（Web UI / VLA / 多机）** | 第一版永远不完成 | 你已经列了"不要做"的清单，**把它写成仓库里的 `docs/non-goals.md` 并让 CI 检查 README 里没出现这些词** |

## 7. 修正后的第一版建议（比原方案更小）

**保留**：Scenario Registry（真 schema）→ ROS 2 Action 适配器 → 4 类故障 → 三态判定 → 证据包 → 判定链重放 + 报告。

**调整**：
1. 故障从"5 类"改为 **4 类 + 1 类降级**：ACK 丢失 / ACK 迟到 / 进程被杀 / 任务超时 + **取消-完成竞争**；资源 claim 以"框架侧租约表"实现并标注作用域。
2. 适配器**只做 ROS 2 Action**；CAN/gRPC 放第二版，接口先留出。
3. 被测量对象默认是**仓库内自带的确定性假 SUT**（已经写好，能演三种 ACK 行为），EAR 作为**可选真实对象**，编译脚本独立、失败不影响核心验收。
4. "一条命令"必须真的是一条命令，且**在没有 ROS 2 的机器上也要能以 `--mock` 模式跑完并给出 `insufficient_evidence` 而不是报错**。

**新的验收条件（可机械检查）**：
- [ ] `pip install -e .[dev] && pytest` 全绿（不是 44 个收集错误）
- [ ] `assurance doctor` 输出每个后端的 `available/unavailable + 原因`
- [ ] `assurance run --scenario cancel-vs-complete --seed 7 --mock` 在**无 ROS 2** 环境产出证据包
- [ ] `assurance run --scenario ack-late --transport ros2action` 在**有 ROS 2** 环境产出 `refuted(late_ack_from_previous_epoch)`
- [ ] `assurance replay <bundle>` 对 `deterministic/` 部分逐字节一致
- [ ] 故意删掉一条证据 → 判定自动变 `insufficient_evidence`，且报告指出缺哪条
- [ ] 报告里每个非 `confirmed` 都有一句人类可读的失败原因（不是 "failed"）

## 8. 你要做的三个决定

1. **新仓库 vs 升级旧仓库**：建议新仓库 + 搬迁 4 个模块（§4.2）。若要"少一个仓库"，次优是把 `workbench` 的打包缺陷修掉再原地扩，但那要先花时间修 44 个收集错误和命名空间冲突。
2. **被测量对象默认是谁**：建议默认自带假 SUT，EAR 为可选 real-device profile。
3. **CAN 后端要不要进第一版**：本机 vcan 不可用，强行做只能做到 python-can virtual bus 的层面。建议第一版只留接口 + `doctor` 探测，第二版再接 EAR 的 `virtual_can_device`。
